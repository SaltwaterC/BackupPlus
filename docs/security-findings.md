# Security review findings

This document records the findings of a source security review of BackupPlus carried out on 2026-10-30 against commit `c1c11179`. Each finding has an identifier, a severity, a status and remediation criteria that describe what a fix must achieve. A status of **Open** means the issue is present in the reviewed code; documentation alone does not mean a fix has been implemented. Update the status (and the commit that fixed it) when a finding is resolved, and keep resolved findings in place so the identifiers stay stable.

Line numbers refer to the reviewed commit and will drift as the code changes; the function and file names are the stable reference.

## Scope and method

The review covered plugin code in the repository root, `includes/`, `methods/`, `templates/`, `js/`, `includes/admin-common/` and `assets-src/decryption/`. Bundled third-party SDKs (`methods/googledrive/Google`, `methods/dropbox/Dropbox2`, `methods/cloudfiles/sdk`, `vendor/`) were reviewed only for TLS configuration and for how the plugin calls them. WP-CLI commands were not reviewed as an attack surface, because a WP-CLI user already has shell access. `tests/`, `scripts/` and `dev/` were out of scope except where `scripts/check-sql.php` enforces a security rule.

The review was split into five areas: authentication, authorization and CSRF on every entry point; cryptography and secret handling; SQL injection and database privilege; filesystem, archive, upload/download and process execution; and remote storage, outbound HTTP and output escaping. Every finding of Low severity or above was traced through the code; findings marked *confirmed* were re-read at the cited lines after the initial report. No code was changed and no exploit was run against a live site. The only dynamic check was a `whois` lookup for BPS-01 and a local PHP check that `fopen()` resolves `missing/../` textually (BPS-02).

### Threat model

BackupPlus restricts its administration to `manage_options` on a single site and to `manage_network_options` on the main site of a network (`BackupPlus_Options::user_can_manage()`, `includes/class-multisite.php`). Those administrators are trusted. The attackers that matter are:

* unauthenticated visitors and low-privileged users (subscribers, authors, multisite sub-site administrators);
* a third party who can trick a logged-in administrator into opening a link or page (CSRF);
* anyone who can write to a configured remote storage destination without being a WordPress administrator: a bucket shared between sites, a leaked or narrowly-scoped storage credential, the storage provider, or a network attacker on a plaintext transport;
* anyone who obtains a copy of a backup or database dump, which is the threat that credential encryption is designed for;
* other local users on shared hosting;
* whoever controls a hostname the plugin trusts.

### Severity scale

| Severity | Meaning |
| --- | --- |
| Critical | Unauthenticated compromise of the site or its data with no user interaction. |
| High | Compromise of backups, credentials or the site by an outside party with little or no precondition. |
| Medium | Compromise that needs a realistic precondition, such as write access to remote storage or an administrator following a link. |
| Low | Requires an unusual configuration, an already-trusted actor, or local access; or a defence-in-depth gap that is not exploitable today. |
| Info | Hardening opportunity, documentation mismatch or tooling gap. |

## Summary

No Critical finding was identified, and nothing was found that an unauthenticated visitor can exploit without first obtaining a secret. The most serious issue was a hardcoded OAuth relay hostname that anyone can register; it is fixed. Three Medium findings share a root cause: data listed from remote storage (file names, archive contents, PITR chains) is trusted as if the site had produced it.

## Findings

### BPS-01: OAuth relay hostname is unregistered

**Severity:** High. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `methods/googledrive.php:80` (`callback_url`), `methods/googledrive/client.php:36-100` (`bootstrap()`), `methods/googledrive/client.php:351` (`use_master()`), `methods/dropbox/client.php:148` (`$callback`), `methods/dropbox/Dropbox2/OAuth/Consumer/ConsumerAbstract.php:235,284-306`.

**Description.** Google Drive and Dropbox support a "master app" mode in which a relay service holds the OAuth client secret and hands tokens to the site. The relay URL defaults to `https://auth.backupplusplus.com/...` unless `BACKUPPLUS_GOOGLEDRIVE_CALLBACK_URL` or `BACKUPPLUS_DROPBOX_AUTH_RETURN_URL` is defined. The hostname is a rename artefact of `auth.updraftplus.com`. On 2026-10-30, `whois backupplusplus.com` returned "No match for domain" and the name did not resolve, so anyone can register it.

Google Drive uses master mode whenever no custom client ID and secret are saved and `BACKUPPLUS_CUSTOM_GOOGLEDRIVE_APP` is not defined. In that mode every `bootstrap()` posts the saved `user_id` to the relay, base64-decodes `$body[0]` of the response, and uses the `access_token` it contains for all uploads, listings and deletions. Dropbox with the default app key sends the site's `refresh_token` to the relay in `refreshAccessToken()` and stores whatever `access_token` and `expires_in` come back. The Dropbox `getAccessToken()` path also accepts a base64 JSON token blob supplied directly as the OAuth `code`.

Sites enter this mode by default when an administrator connects Google Drive without entering a custom app. The settings importer (`includes/class-settings-importer.php:141-155`) also maps `updraft_googledrive` and `updraft_dropbox` from UpdraftPlus exports, so a site imported from UpdraftPlus with its master apps lands in master mode with a live `user_id` or refresh token. BPS-05 can additionally write `user_id` without the administrator's knowledge.

The plugin also ships UpdraftPlus's Google client ID and its Dropbox app key and secret (base64-encoded in `methods/dropbox.php:131` and `methods/dropbox/client.php:142`). These are third-party credentials that BackupPlus does not control.

**Exploit scenario.** An attacker registers `backupplusplus.com` and serves `/auth/googledrive` and `/auth/dropbox/`. Every BackupPlus site in Google Drive master mode now asks the attacker for an access token on each run; the attacker returns a token for an attacker-owned Drive, and every subsequent backup (database including `wp_users`, `wp-config.php`, uploads, plugins) is uploaded to the attacker. Dropbox default-app sites send their refresh tokens to the attacker. New administrators who click "authenticate" are redirected to the attacker's site, which can complete the flow with attacker-owned credentials.

**Remediation criteria.**

* No code path sends tokens, refresh tokens, user IDs or authorization codes to a hostname that the project does not control.
* Either the master-app paths for Google Drive and Dropbox are removed and a custom app is required, or the relay hostname is one the maintainers own and operate, with its renewal tracked.
* Embedded UpdraftPlus client IDs, app keys and secrets are removed.
* Importing UpdraftPlus master-app settings does not silently produce a master-mode connection; the destination is marked as needing re-authentication with a custom app.
* A regression test asserts that no plugin file contains a relay hostname outside an allowlist.

**Resolution.** The relay and both master-app paths are removed, along with the embedded UpdraftPlus client ID, app key and secret. Every criterion above is met:

* Google Drive requires the site's own OAuth client. Its redirect URI is the site's own settings page (`methods/googledrive/oauth.php`), and the access token is obtained from the refresh token directly with Google. Connections made through the shared client are not used for transfers and raise a dashboard notice until they are signed in again with an own client (`methods/googledrive/admin.php`).
* Dropbox uses OAuth with PKCE and a pasted code (`methods/dropbox/pkce.php`): the authorization page displays the code, the administrator pastes it into the settings page (or passes it to `wp backupplus remote authorize dropbox`), and the site exchanges it with `api.dropboxapi.com` using the PKCE verifier. Neither a redirect URI nor an app secret is involved, so a built-in app key can be shipped safely; it is empty until a BackupPlus Dropbox app is registered, and `BACKUPPLUS_DROPBOX_CLIENT_ID` or a per-connection app key replaces it. The verifier is stored with the instance's encrypted tokens and expires after ten minutes. Tokens are renewed directly with Dropbox, without a secret for PKCE tokens. Tokens issued to the shared upstream app are refused and the connection is marked as needing to be connected again.
* The settings importer drops Dropbox tokens of instances without their own app key; imported Google Drive shared-client connections get the notice above.
* `tests/Unit/Providers/DropboxPkceTest.php` covers the PKCE request, exchange, renewal and the refusal of legacy tokens; `tests/Unit/Providers/GoogleDriveOwnClientTest.php` covers the own-client rules and scans `methods/`, `includes/` and the top-level plugin files for the relay hostname and the upstream client identifiers.

The pasted code is protected by PKCE: a code obtained by anyone else cannot be redeemed without the verifier held by the site. The old relay-based "manual authentication" that accepted tokens and user IDs directly is removed.

### BPS-02: Remote file names can traverse out of the backup directory

**Severity:** Medium. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `includes/backup-history/trait-rebuild.php:165` and `:440` (`rebuild()` name pattern), `methods/s3/base.php:781-786` (and the identical code in `methods/s3generic/` and `methods/dreamobjects/`), `includes/class-storage-methods-interface.php:327` (`get_remote_file()`), `includes/core/trait-remote-transfer.php:242-252` (`chunked_download()`), `includes/admin/trait-downloads.php:165-194`, `includes/restorer/trait-run.php:254-267`.

**Description.** "Rescan remote storage" adds every listed object whose name matches `^backup_([\-0-9]{15})_.*_([0-9a-f]{12})-([\-a-z]+)([0-9]+)?(\.(zip|...))?$` to backup history. The `.*` accepts `/`, `\` and `..`. When an S3-family destination has a bucket sub-path, `listfiles_with_path()` strips the prefix but does not drop keys that still contain `/`; only the no-path branch filters them. OpenStack and Cloud Files also appear not to filter `/`; Dropbox and FTP were not confirmed either way.

The history entry is then used verbatim. `get_remote_file()` and `chunked_download()` build `backups_dir_location() . '/' . $file` and open it with `fopen( $fullpath, 'c+' )`; the restore path and the download handler's `delete` stage build the same path. The docblocks describe `$file` as a basename, but nothing enforces it. PHP resolves `missing-dir/../` textually, so the intermediate directory in the name does not need to exist.

The newer providers built on `BackupPlus_Remote_Storage_Module` (Azure, Backblaze, Google Cloud, OneDrive, pCloud) and SFTP/WebDAV reject `/` through `valid_filename()` and are not affected. `class-chain-downloads.php`, `class-backup-deletion.php` and retention use basename checks and are not affected.

**Exploit scenario.** An attacker with write access to the configured bucket prefix creates an object named `prefix/backup_2024-01-01-0000_x/../../../../var/www/html/wp-content/plugins/x/y.php._abcdef012345-db.gz`. When an administrator rescans remote storage (database restore also calls `rebuild( true )`, `includes/restorer/trait-database-restore.php:1057`) and then clicks Download or Restore for that entry, the attacker's bytes are written to the traversed path. The final component must still match the pattern's suffix, so a plain `.php` or `.htaccess` name is not possible, but `name.php._<hex>-db` is executed as PHP on Apache configurations that use `AddHandler`, and any existing file matching the pattern can be overwritten or, through the `delete` stage, unlinked. Unlike planting a malicious archive, this needs only a download, not a restore.

**Remediation criteria.**

* `rebuild()` rejects names containing `/`, `\`, NUL or `..`, before they reach history.
* Every sink that joins a history file name to the backup directory (`get_remote_file()`, `chunked_download()`, the download handler including its `delete` stage, restore) asserts `basename( $file ) === $file` and the backup-name pattern, independently of `rebuild()`.
* S3, S3-generic, DreamObjects, OpenStack, Cloud Files, Dropbox and FTP listings drop names containing a path separator after removing the configured prefix.
* A test lists a remote name containing `../` and verifies it is neither added to history nor written outside the backup directory.

**Resolution.** Remote names are validated where they enter history and again at every sink that joins a history name to the backup directory. Every criterion above is met:

* `BackupPlus_Manipulation_Functions::is_safe_basename()` accepts a single path component only: no `/` or `\`, no NUL or other control character, and no `..`. `is_backup_basename()` additionally requires the backup-archive or PITR-artifact name pattern (`BACKUP_NAME_PATTERN`, `PITR_NAME_PATTERN`).
* `rebuild()` applies `is_safe_basename()` and the archive pattern to every listed remote name, in both the listing loop and the pass that adds remote-only sets.
* `get_remote_file()` and `chunked_download()`, which write remote bytes locally, require `is_backup_basename()`. The local-only sinks require `is_safe_basename()`, because history also holds foreign archives found in the backup directory, whose names follow no BackupPlus pattern. Those sinks are the download handler (before the `delete` and spool stages), the restorer, the restore pre-check and backup set deletion (`includes/admin/trait-backup-sets.php`, which also unlinked history names and was not listed above). A later review found five more sinks, which now check the name too: uploading a local set to remote storage (`upload_local_backup()` in `includes/commands/trait-backups.php`, which also requires the set to exist and every archive name to pass `is_backup_basename()`), `delete_local()` (`includes/core/trait-remote-transfer.php`), the zip browser's archive lookup (`includes/wpadmin-commands/trait-jstree.php`), and the database name read by the restore analysis and the multisite check (`includes/core/trait-database-analysis.php`, `includes/class-multisite-restore.php`).
* The S3, S3-compatible and DreamObjects listings apply the same rule below a bucket sub-path as at the bucket root. OpenStack, Cloud Files (both modules), FTP and Dropbox drop names that are not plain basenames, as does Google Drive, whose file titles may contain `/`. `is_backup_basename()` also refuses a name with an executable or document part anywhere (`EXECUTABLE_NAME_PATTERN`, as for uploads in BPS-06), so a rescan cannot add `backup_….php.zip` either.
* `tests/Unit/Backup/RemoteFileNamesTest.php` covers the validator. The S3, Swift and Dropbox provider tests list traversing, backslash, NUL and sub-folder names and expect only the plain archive. `scripts/check-remote-file-names.php` runs in WordPress as part of `make test`: the shipped S3 module lists a sub-path holding the exploit name through a fake transport. The script checks that a remote rescan adds only the plain archive, and that history poisoned before the fix is refused by `get_remote_file()`, `chunked_download()`, the download handler and its `delete` stage, and set deletion. The legitimate archive still downloads, and a file outside the backup directory at the traversal target survives. Each layer was confirmed to fail that script when reverted on its own.

`fopen()` resolves a missing directory followed by `..` textually, as noted above, but `is_file()` and `unlink()` go through `stat()` and need the directory to exist. The script therefore creates it before checking the deletion sinks.

### BPS-03: PITR source restore runs untrusted SQL with server-level privileges

**Severity:** Medium. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `includes/pitr/trait-history.php:199-270` (`rescan()`), `includes/class-pitr-storage.php:184` (default encryption `none`), `includes/pitr/trait-recovery-plan.php:135-174` (`authenticate()`), `includes/pitr/trait-recovery.php:44` and `:249-251`, `includes/class-pitr-database.php:338-348` (`import()`), `includes/class-pitr-isolation.php:73`.

**Description.** PITR rescan imports chains from remote storage and marks them `'imported' => true`. Their integrity check compares artifacts with the manifest that came from the same storage, so nothing held by the site anchors them. PITR archives are plaintext by default; with age encryption, anyone holding the recipient public key can still produce a valid archive.

A full source restore runs `DROP DATABASE`, then `import( $sql, null, $direct )`. `import()` pipes the baseline into the `mysql` client as the restore account with `--binary-mode`. Because `$database` is `null`, no `--database` is passed, and the only content check on the baseline is a regex in `trait-recovery.php:131` that rejects EVENT statements. DEFINER clauses are kept. In reconstruct mode, the export from the disposable server also keeps `DEFINER=` and is imported through the restore connection.

Per `docs/binary-log-backups.md`, the restore account holds CREATE USER, SUPER or CONNECTION_ADMIN, SET_ANY_DEFINER (SET USER on MariaDB), REPLICATION_APPLIER and related grants, and `class-pitr-isolation.php:73` accepts `ALL PRIVILEGES`. The ordinary restorer, by contrast, runs as the WordPress account, strips DEFINER from routines, views and triggers, and forces `SQL SECURITY INVOKER`.

**Exploit scenario.** An attacker with write access to remote storage plants a chain whose manifest names `DB_NAME`, the right table prefix and a plausible snapshot coordinate, with a baseline containing `CREATE USER ...`, `ALTER USER` on a DBA account without SYSTEM_USER, or `CREATE DEFINER=bp_restore@localhost PROCEDURE wordpress.p() SQL SECURITY DEFINER ...`. An administrator rescans (typically during disaster recovery on a fresh site) and restores that point. The SQL runs as the restore account; a SQL SECURITY DEFINER routine owned by it remains in the WordPress schema, and anyone who later controls the WordPress database account can call it with the restore account's server-level rights.

**Remediation criteria.**

* Source restore (restore onto the live database) accepts only chains captured by this site, or chains whose manifest is authenticated with a key held by the site and not stored with the backups. Imported chains remain available for isolated export.
* Baseline and reconstructed exports are imported with `--database=DB_NAME`.
* DEFINER clauses are removed or rewritten to the WordPress application account and `SQL SECURITY INVOKER` is forced, matching the ordinary restorer.
* Statements that change accounts, grants or global server state (`CREATE/ALTER/DROP USER`, `GRANT`, `REVOKE`, `SET GLOBAL`, `SET PASSWORD`, `INSTALL PLUGIN` and similar) cause the restore to fail before anything is dropped.
* A test restores a planted chain containing each of these statements and verifies that the restore is refused and the database is untouched.

**Resolution.** Source restore now refuses chains the site did not capture, and checks and rewrites the SQL it imports before anything is changed. Every criterion above is met:

* `restore()` (direct and staged) and `verify_source_restore()` refuse chains marked `imported`, which covers every chain added by a rescan. The refusal points to `wp backupplus pitr recover`, which still exports such a chain to an isolated recovery server for the ordinary importer. The manifest-authentication alternative was not implemented. A key kept with the backups would not authenticate anything. A key kept only on the site is lost in the disaster that makes a rescan necessary.
* The restore imports the checked baseline or reconstructed export, and the replay SQL, with `--database=DB_NAME`. `import()` also passes `--local-infile=0` and `--default-character-set=utf8mb4` next to `--binary-mode`. The dump's own `CREATE DATABASE` and `USE` statements are dropped. A whole-database restore recreates the database from fixed templates with the character set, collation and encryption that the dump's `CREATE DATABASE` declared.
* `BackupPlus_PITR_SQL_Guard` (`includes/class-pitr-sql-guard.php`) rewrites the DEFINER of every view, trigger, routine and event to the WordPress connection's `CURRENT_USER()`, and removes any DEFINER or SQL SECURITY clause from the dump. Views are created with `SQL SECURITY INVOKER`, and each procedure and function is followed by `ALTER ... SQL SECURITY INVOKER`. Triggers and events have no SQL SECURITY clause; they run as the WordPress account.
* The guard runs in `restore_locked()` before isolation, the pre-restore snapshot, maintenance mode and `DROP DATABASE`. It also runs in `verify_source_restore()`. It accepts only what `mysqldump` and `mariadb-dump` write for one database: definitions, `DROP`, `LOCK`/`UNLOCK TABLES`, `ALTER TABLE ... DISABLE/ENABLE KEYS`, `INSERT`/`REPLACE ... VALUES` with literal values only, MariaDB `SETVAL`, and session `SET` of plain values or variables saved from the same setting. Any other statement fails the restore, as does any name qualified with another database. A session `SET` assigns one plain value or variable, never an expression. `sql_log_bin` may only be turned off or set back to a saved value, a storage engine setting must name InnoDB, MyISAM, Aria or MEMORY, and replication and debugging internals (`gtid_next`, `pseudo_thread_id`, `server_id`, `debug_sync` and others) cannot be set. The bodies of views, triggers and routines are checked as well: account, role and privilege statements, dynamic SQL (`PREPARE`, `EXECUTE`), server administration (`SHUTDOWN`, `KILL`, `FLUSH`, `PURGE`, `RESET`, plugins), file access, `USE`, global settings, names in `mysql`, `sys` and `performance_schema`, and three-part names of another database are refused there. The scanner splits statements exactly as the `mysql` client does in binary mode, including its `delimiter` command and the version-dependent `/*!` and `/*M!` comments, and refuses input on which a server could disagree. That covers `ANSI_QUOTES`, `NO_BACKSLASH_ESCAPES`, multibyte client character sets such as `gbk`, nested comments, optimizer hints and `--` followed by a control character. The binary-log replay SQL is not passed through the guard: `mysqlbinlog` produces it from row events, and account-administration events are already neutralised in the private replay copies.
* The restore refuses an account named `root` or one holding `ALL PRIVILEGES ON *.*` (`includes/class-pitr-isolation.php`), so the privileges the replay runs with are those `docs/binary-log-backups.md` documents and no more.
* `tests/Unit/Pitr/PitrSqlGuardTest.php` checks the rewrites and dropped statements on real MySQL 8.4 and MariaDB 11.4 dumps, with row data copied byte for byte. It also checks that 68 privileged statements and 24 splitting attacks are refused and leave no checked copy behind. In the native matrix, `scripts/check-pitr-planted.php` builds a chain from the real baseline for each statement in the criterion, plus a write to `mysql.db` and a `USE mysql`. After a rescan, direct restore, staged restore and verification refuse each chain as not captured by this site. The same chains, marked as captured, are refused by the SQL check. In both cases the application tables, `mysql.user`, the planted grants, `max_connections`, the maintenance file and the chain index are unchanged, and no pre-restore snapshot is taken. `scripts/check-pitr.php` also refuses a rescanned genuine chain, exports it in isolation, and checks after a direct source restore that every view, routine, trigger and event belongs to the WordPress account with invoker security.

### BPS-04: Stored XSS from remote storage and archive contents

**Severity:** Medium. **Status:** Fixed. **Confirmed** for sinks (a), (b), (f) and (g); traced for the others. The locations below refer to the code as reviewed.

**Location and description.** File names accepted by `rebuild()` (see BPS-02) may contain `<`, `>`, quotes and spaces, and are written to history unescaped. Archive entry names, dump header comments and remote error messages are also attacker-influenced. They reach these sinks without escaping:

* (a) `includes/admin/trait-existing-backups.php:873`: the Advanced Tools "Known backups (raw)" output is `var_dump( $history )` inside `<pre>` with no escaping, served as HTML.
* (b) `includes/admin/trait-existing-backups.php:32` and `:103`: `$backup['label']` and `print_r( $backup )` in the raw backup info. `rawbackup_history` (`includes/commands/trait-backups.php:176`) applies `html_entity_decode()`, and `includes/admin-common/ready-tools.js:11-12` passes the result through `textarea.innerHTML` and `.value` into `backupplus_html_modal`, which uses `.html()` (`includes/admin-common/modals.js:65`). Triggered when the administrator double-clicks the backup date.
* (c) The log line `Requested file from remote service: $service: $file` (`includes/class-storage-methods-interface.php:412`) is stored as `dlmessage` (`includes/core/trait-logging.php:293`) and rendered with `.html()` in `restore-status.js:176,182,197`.
* (d) Restore preflight errors and warnings that include `$file` (`includes/wpadmin-commands/trait-restore.php:144,147,153`) and database-scan warnings that copy `# Skipped tables:`, `SET NAMES`, the old site URL and the foreign-dump `# Label:` line (`includes/core/trait-database-analysis.php:171,278,313,316,413`) are rendered with `.html()` in `restore-status.js:43-91`.
* (e) `js/backupplus-admin-restore.js:166,168` render `restore_data.data.table` and `.routine_name` from the dump with `.html()`.
* (f) The zip browser and exclusion picker use jstree without `force_text`, so `includes/jstree/jstree.js:2615` assigns entry names through `innerHTML`. Names come from archive entries and from `readdir()` (`includes/wpadmin-commands/trait-jstree.php:55,79,86,238`).
* (g) `methods/googledrive/oauth.php:392` concatenates the Google account display name into the success notice, and `:351` concatenates error messages; `show_admin_warning()` does not escape them. *Fixed with BPS-01: both are now escaped.*
* (h) Rescan error messages (`includes/admin/trait-backup-sets.php:405`) print `$msg['message']`, which carries OpenStack and Dropbox exception text.

**Exploit scenario.** A bucket writer creates an object named `backup_2024-01-01-0000_<img src=x onerror=...>_abcdef012345-db.gz`. * jstree is configured with `core.force_text: true` everywhere it is instantiated.
* `show_admin_warning()` callers pass escaped text, or the function escapes and callers opt in to markup explicitly.
* BPS-02's name validation is in place, so history names cannot contain markup.
* A test renders each sink with a name containing `<img src=x onerror=...>` and asserts the markup is escaped.

**Resolution.** Every sink escapes its data where it is added to the output, and no layer decodes the result again. Every criterion above is met, with one difference in how the name criterion is met, noted below:

* (a) `show_raw_backups()` passes the `var_dump()` output through `esc_html()`, and escapes the backup directory listing (the entry name, and the log-download link) as well.
* (b) `raw_backup_info()` escapes the label, key, date, service names and the `print_r()` of the history entry and job data, and returns the markup as is. It no longer wraps the result in `esc_attr()`, which kept existing entities and so could not protect the markup once it was decoded; nothing used that return value as an attribute. `rawbackup_history` and `always_keep_this_backup` no longer call `html_entity_decode()`, and `ready-tools.js` no longer decodes through `textarea.innerHTML`. The checksum values and external-database details that `get_entity_row()` prints in the same view are escaped too; they were not in the list above, and the check found the checksum value to be a further sink.
* (c) The download status message, which carries the log line, is escaped by `download_status()`.
* (d) The restore preflight escapes the file names in its errors and warnings, the unknown-source label and the PHP messages collected during the scan. The database scan escapes the old site URL, the backup label, the skipped and missing tables, the character sets and collations, the version strings from the dump header and the creating-version string.
* (e) The restore progress labels escape the table and routine names (`js/backupplus-admin-restore.js` and the minified source that the shipped build is generated from, `assets-src/js/backupplus-admin-restore.min.js`).
* (f) Every jstree instance (the zip browser, the two exclusion pickers and the remote folder picker) sets `core.force_text`, so names from archives, `readdir()` and remote folder listings are rendered as text.
* (g) Fixed with BPS-01.
* (h) The rescan messages escape the method description and message, including plain-string messages.
* `show_admin_warning()` still does not escape; its callers were audited. Those that include data from outside the site (the Dropbox account name and the Google Drive display name and error text) already escape it, and the rest pass fixed or translated text.
* BPS-02's name validation rejects separators, `..` and control characters, but not `<`, `>` or quotes, which a legitimate site name could contain. History names can therefore still contain markup, and the criterion that they cannot is met by escaping at every sink instead.

Reverting the escaping of the download message, the rescan messages, the skipped tables, the old site URL, the preflight warnings and the raw history dump each fails that script. `tests/Unit/Backup/AdminMarkupEscapingTest.php` checks the browser side: every script that creates a jstree sets `force_text` (including the built bundle), the decoding steps are gone, and the progress labels escape the dump's names in both the source and the minified build.

### BPS-05: Dropbox and Google Drive OAuth callbacks lack `state` validation

**Severity:** Medium. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `methods/dropbox/oauth.php:36-48,76-102`, `methods/googledrive/oauth.php:11-52,192-218,244-306`, `includes/core/trait-wordpress-hooks.php:155-200`.

**Description.** OAuth callbacks are dispatched on `admin_init` for any user who passes `user_can_manage()`, with no nonce, by GET or POST.

Dropbox compares `strcmp( $csrf, $state ) == 0`, where `$state` is the text before the first `:` in the `state` parameter. After a completed authorization `$opts['CSRF']` is set to `''`, and before any authorization it is unset. A callback with `state=:<instance_id>` therefore passes, and the attacker's `code` is stored. With the default app, `getAccessToken()` decodes that code directly into an access and refresh token without an exchange. If the instance already has a token, the planted code stays in `$opts['code']` and is consumed on the next re-authorization. On mismatch, the expected CSRF value is written to the PHP error log.

Google Drive has no state check at all. `state=success:<id>&user_id=...&access_token=...` writes `user_id` and `tmp_access_token`, without requiring `auth_in_progress`; `state=token:<id>&code=...` exchanges an attacker-chosen authorization code; `state=revoke:<id>` revokes and wipes the token.

OneDrive and pCloud implement this correctly: a 256-bit random state, stored hashed, bound to the user, expiring after 10 minutes, single use, compared with `hash_equals()`, and the flow is started with a nonce.

**Exploit scenario.** An attacker who knows a storage instance ID gets a logged-in administrator to load `wp-admin/options-general.php?page=backupplus&action=backupplusmethod-dropbox-auth&state=:<instance_id>&code=<base64 JSON of an attacker token>`, for example through an image tag or auto-submitting form on another site. The destination is silently rebound to the attacker's Dropbox and every later backup is delivered to them. The Google Drive `revoke` variant silently stops Drive backups; the `success` variant combines with BPS-01 and BPS-04 (g).

The precondition is the instance ID (`s-` plus an MD5 of random values, `includes/class-storage-methods-interface.php:519`). It is not guessable, but it is not treated as a secret: it appears in admin HTML, settings exports and logs. If one leaks, this becomes High.

**Remediation criteria.**

* Dropbox and Google Drive use the OneDrive/pCloud state scheme: random state generated when the flow starts, stored hashed and bound to the user and instance, single use, short expiry, compared with `hash_equals()`. An empty or missing state is rejected.
* Google Drive `success`, `token` and `revoke` all require a valid pending state; `revoke` additionally requires a nonce because it is not an OAuth return.
* CSRF comparison failures do not log the expected value.
* Tests cover an empty state, a reused state, a state for another user and an expired state.

**Resolution.** Dropbox no longer has an OAuth callback, and Google Drive uses the OneDrive/pCloud state scheme. Every criterion above is met:

* Dropbox was fixed with BPS-01. Its `doit` action only starts a PKCE authorization. The administrator pastes the code that Dropbox displays, which is accepted only through the nonce-checked `backupplus_ajax` dispatcher or WP-CLI, and it can be redeemed only with the PKCE verifier the site generated. The `CSRF` and `code` options and the code that compared and logged them are gone.
* Google Drive's `authorization_url()` (`methods/googledrive/oauth.php`) creates the state `token:<instance>:<256 random bits>` when the nonce-checked `doit` action starts a sign-in. It stores only its SHA-256 hash, with the current user and an expiry ten minutes ahead, in that instance's options. The state is added after the `backupplus_googledrive_auth_params` filter runs, so the filter cannot remove it. The hash is hidden from the settings templates.
* `complete_oauth()` handles `state=token`. It removes the stored state before any check, so each state can be used once and a failed attempt ends the pending sign-in. It then requires a non-empty string state, the same user, an unexpired entry and a match by `hash_equals()`. Only then is the code sent to Google. Because the hash covers the instance ID, a state is valid only for the instance that issued it. A refusal is logged without the expected value.
* `state=revoke` is no longer handled. Nothing linked to it. Revocation happens only through the nonce-checked `doit` (before a new sign-in) and `deauth` actions.
* The `success` state no longer accepts tokens (BPS-01). It now only shows the result of a sign-in that has just been completed, a step that has no OAuth state of its own. The redirect to it carries a WordPress nonce, and the notice is shown only when the nonce is valid.
* `tests/Unit/Providers/GoogleDriveOAuthStateTest.php` covers an empty, missing or non-string state; a reused state; a state for another user; an expired state; a forged state and the old instance-only format; a wrong state followed by the right one; this instance's state replayed for another instance; and a return without a code. In each case it checks that nothing is sent to Google and that the existing connection is unchanged. It also checks that the state is not stored in clear, that a filter cannot remove it, that `state=revoke` leaves the connection in place and that the success notice requires the nonce. Reverting the hash, user, expiry or single-use check, the state parameter or the nonce check each fails that test.

### BPS-06: Backup uploads can store PHP files

**Severity:** Low. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `includes/admin/trait-uploads.php:89-94`, `:125`, `:174-175`.

**Description.** The upload handler checks `$_POST['name']` against `^log\.[a-f0-9]{12}\.txt` or the backup-name pattern. The log pattern has no end anchor, so `log.abcdef012345.txt.php` passes, and a chunked upload with that name is assembled into `<backup directory>/log.abcdef012345.txt.php`. For a non-chunked upload, the stored file name comes from `$_FILES['async-upload']['name']` through `wp_handle_upload()` with `test_type => false`, while only `$_POST['name']` is validated; a valid POST name with a `shell.php` file part stores `shell.php`. Both bypass WordPress's usual block on PHP uploads by users without `unfiltered_upload`.

**Exploit scenario.** Requires an administrator and a nonce, so the impact is executing PHP where the site's hardening (`DISALLOW_FILE_EDIT`, `DISALLOW_FILE_MODS`, no `unfiltered_upload`) intends to prevent it. The backup directory's `.htaccess` blocks access on Apache; on nginx, or Apache with `AllowOverride None`, the random-named directory is served and the file executes. With BPS-07 it works on any server.

**Remediation criteria.**

* Both patterns are anchored at the end, and the extension is checked against an allowlist.
* The stored file name is the validated name, not the client-supplied multipart file name.
* A test uploads `log.<hex>.txt.php` and a mismatched `$_FILES` name and verifies both are rejected.

**Resolution.** Both uploaders validate the name and chunk numbers of every part before anything is written, and the file is stored only under the validated name. Every criterion above is met:

* `BackupPlus_Manipulation_Functions::upload_name()` requires a safe basename (`is_safe_basename()`) and one of: a log name matching `LOG_NAME_PATTERN` (`\Alog\.[a-f0-9]{12}\.txt\z`), a BackupPlus archive matching `BACKUP_NAME_PATTERN` that has one of its archive extensions (names without an extension, which rescans tolerate, are refused for uploads), or a name that a `backupplus_accept_archivename` entry recognises and that ends in an archive extension (`FOREIGN_ARCHIVE_EXTENSION_PATTERN`). Any dot-separated part that web servers commonly execute (`.php`, `.phtml`, `.phar`, `.cgi`, `.user.ini` and others; `EXECUTABLE_NAME_PATTERN`) is refused anywhere in the name, so an Apache handler that matches inner extensions cannot run an upload either. The decrypter uploader (`plupload_action2`) keeps its encrypted-archive pattern, now anchored with `\z`, and applies the same basename and executable-part checks.
* The name is the `name` field that plupload sends, or the multipart file name when that is absent; either way it is validated as above. `store_upload()` replaces the multipart file name with a random `backupplus-upload-<hex>.tmp` before `wp_handle_upload()`, then renames the stored file to the validated name (or to `<name>.<chunk>.zip.tmp` for a chunk). The client's multipart file name never reaches the file system. Chunk numbers must be decimal and below the chunk count. Previously only the final chunk was checked, after every earlier chunk had been stored. The success response now returns the stored name instead of a URL under the uploads directory, which did not point to the file.
* `tests/Unit/Backup/UploadNamesTest.php` covers the name rules. `scripts/check-upload-names.php` runs in WordPress as part of `make test` and sends real multipart uploads to `admin-ajax.php`. It checks that every chunk of `log.abcdef012345.txt.php` is refused, and that a one-part upload of the same name, of `shell.php` with no `name` field, of a valid name with a `.php` suffix, and of a name with an inner `.php.` part are each refused, with nothing stored. It also checks that a valid `name` sent with a `shell.php` file part is stored under the valid name only, and that the decrypter uploader follows the same rules. A mismatched multipart file name is not an error in itself: plupload sends `blob` for every chunk. The script fails against the previous handler.

### BPS-07: Backup directory setting accepts any location

**Severity:** Low. **Status:** Fixed. The locations below refer to the code as reviewed.

**Location:** `includes/class-manipulation-functions.php:252`, `includes/core/trait-entities.php:362-381`, `includes/filesystem-functions/trait-files.php:122-170`.

**Description.** The `backupplus_dir` setting accepts absolute paths and relative paths containing `..`. Once set, the plugin writes `index.html` (overwriting an existing one), `.htaccess` with `deny from all` if none exists, and `web.config` into that directory, and the temporary-file cleanup deletes `*.tmp` and `zi??????` files older than 12 hours there. Uploads (BPS-06) also go there.

**Exploit scenario.** An administrator on a hardened site sets the directory to `wp-content/mu-plugins` and uploads a PHP file through BPS-06; it is loaded on every request. Setting it to the web root replaces `index.html` and, if no `.htaccess` exists, takes the site offline.

**Remediation criteria.**

* The setting accepts only a single directory name under `WP_CONTENT_DIR` (or a path resolved with `realpath()` that stays inside it and is not a WordPress, plugin, theme or mu-plugin directory), unless a constant explicitly allows another location.
* Protection files are never overwritten; an existing `index.html` or `.htaccess` in a non-empty directory causes the setting to be rejected.

**Resolution.** `includes/class-backup-directory.php` (`BackupPlus_Backup_Directory`) decides where the backup directory may be, and both the setting and the resolver use it. Every criterion above is met:

* `sanitize()` is registered on `sanitize_option_backupplus_dir` at plugin load, not only in wp-admin, so the settings page, the settings importer, WP-CLI and `wp option update` are all checked. A new value must be a single folder name (`NAME_PATTERN`) directly inside `WP_CONTENT_DIR`. An absolute path inside it, or a `wp-content/` prefix, is reduced to the name first. The name cannot be `plugins`, `mu-plugins`, `themes`, `uploads`, `languages`, `upgrade` or another reserved name, or the credential key folder. Resolved with `realpath()`, it must stay directly inside `WP_CONTENT_DIR` (a link elsewhere is refused). It cannot equal, contain or lie inside ABSPATH, `wp-content`, `wp-admin`, `wp-includes`, the plugin, must-use plugin, theme or uploads folders, or the BackupPlus plugin folder (`unsafe()`). A refused value keeps the saved one and reports why through `add_settings_error()`, which the AJAX settings save now shows. Another location can only be chosen with `BACKUPPLUS_BACKUP_DIRECTORY` in `wp-config.php`; while it is defined the setting cannot change, and the settings field is read-only.
* A new value naming an existing folder that has an `index.html` or `.htaccess` BackupPlus did not write is refused. Accepted files are BackupPlus's or UpdraftPlus's `index.html`, and an `.htaccess` that only denies access. A later review added two refusals. A name ending in an executable extension (`EXECUTABLE_NAME_PATTERN`, such as `db.php` or `object-cache.php`, the names of WordPress drop-ins) is refused. An existing non-empty folder without an `index.html` is refused unless it already holds BackupPlus backups or logs, so another plugin's folder cannot be taken over and its files cleaned up. `backups_dir_location()` creates missing `index.html`, `.htaccess` and `web.config` files with exclusive creation (`protect()`) and never replaces an existing file or link.
* Defence in depth: the resolver applies `unsafe()` to the saved value and to the constant whatever their origin, so a value saved before this fix that names one of those folders leads to the default folder instead. A safe value saved earlier, such as an absolute path outside `wp-content`, keeps working while it is unchanged; the settings form sends it back on every save. Changing it to another such location requires the constant.
* `tests/Unit/Backup/BackupDirectoryTest.php` covers the name rules, links, folders with their own protection files, the constant and unsafe saved values. `scripts/check-backup-directory.php` runs in WordPress as part of `make test`. It saves through `update_option()` and checks that `mu-plugins`, the plugins, theme and uploads folders, the web root, `wp-content`, a folder outside it, traversal and a folder with its own `index.html` are refused with an error. It also checks that unsafe saved values lead to the default folder, that existing protection files are kept, that no protection file appears in a WordPress folder, and that the constant works. `check-upload-names.php`, `check-age-encryption.php` and the browser restore fixture now keep their disposable backup directories directly in `wp-content` instead of inside uploads.

### BPS-08: mysqldump password file is world-readable and injectable

**Severity:** Low. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `includes/backup/trait-database-tables.php:49-50`, `includes/core/trait-binaries.php:36-37`.

**Description.** Before running `mysqldump`, the plugin writes `"[mysqldump]\npassword=\"" . addslashes( $pass ) . "\"\n"` to `<backup directory>/<md5>.tmp` with `file_put_contents()`. The file gets the process umask (typically 0644). `backup_table_bindump()` has no `finally`, so a timeout or fatal error during a long dump leaves the file until the 12-hour temporary cleanup. `addslashes()` does not escape newlines, so a password containing a newline adds arbitrary `[mysqldump]` options such as `result-file=` (write to a chosen path) or `plugin-dir=` with `default-auth=` (load a shared library). The external database password in `backupplus_extradbs` is not checked for control characters (`includes/class-backup-sources.php:130-149`).

The password is correctly kept off `argv`. PITR already handles this safely: credentials go over a file descriptor 3 pipe, option files are 0600, and `\r`, `\n` and NUL are rejected (`includes/class-pitr-process.php:16`).

**Exploit scenario.** On shared hosting, another local account that can list the backup directory reads `DB_PASSWORD` (or an external database's password) while the dump runs or after it is interrupted. The newline injection requires an administrator, so it is a hardening issue.

**Remediation criteria.**

* The option file is created 0600 (or replaced by the PITR file descriptor 3 pipe) and removed in a `finally` block.
* Passwords containing `\r`, `\n` or NUL are rejected when saved and before the file is written, matching `BackupPlus_PITR_Process`.

**Resolution.** `includes/class-mysqldump-option-file.php` (`BackupPlus_Mysqldump_Option_File`) writes the option file for both mysqldump runs, the probe in `find_working_sqldump()` and the per-table dump in `backup_table_bindump()`. Every criterion above is met:

* `create()` opens the file with exclusive creation (`fopen( 'xb' )`) under a 0077 umask, then sets it to 0600 before the password is written. The name is 32 random hexadecimal characters and `.tmp`, so the 12-hour temporary cleanup still matches any leftover. Each caller removes the file in a `finally` block: the dump itself moved into `run_bindump()` and the probe loop into `probe_sqldump()`. Every file is also tracked until it is removed, and a shutdown function removes any that remain, because PHP runs shutdown functions but not `finally` blocks after a timeout or fatal error. Previously a `table_conditions()` error also left the file, because it was written first; the file is now written after that check.
* `contents()` refuses a password with `\r`, `\n` or NUL, so nothing is written for it. Otherwise it quotes the password as `BackupPlus_PITR_Process::memory_connection()` does: `\` and `"` are escaped and nothing else. A refused `DB_PASSWORD` or external database password means the PHP dumper is used, and the log says why. Saved external database passwords are checked in `BackupPlus_Backup_Sources::sanitize_connections()`, now the `backupplus_extradbs` sanitizer for the settings form and WP-CLI. A refused password is not stored, while the rest of the connection is. Storing the old value is not an option, because the settings save clears `backupplus_extradbs` first. The settings save shows the error. `wp backupplus databases set` refuses such a password with an error, `--skip-test` included. `DB_PASSWORD` comes from `wp-config.php`, so it can only be refused when the file would be written.
* The password stays off `argv`. A file descriptor 3 pipe was not used, because these runs go through `popen()` and the `backupplus_mysqldump_arguments` filter, which work on a shell command string.
* `tests/Unit/Backup/MysqldumpOptionFileTest.php` checks the 0600 mode under a 0000 umask, the quoting, the refusal of `\r`, `\n`, NUL and non-string passwords with no file left, cleanup at shutdown, and the sanitizer. `scripts/check-mysqldump-option-file.php` runs in WordPress as part of `make test`. It checks with the real mysqldump (`--print-defaults`) that a password with quotes, backslashes, `#` and `;` is read unchanged as the only option. It also checks that refused passwords leave no file, and that the probe dumps the options table with `DB_PASSWORD` and leaves no option file. Finally, it checks that saving an external database with a line break in its password keeps the connection without the password and reports the error.

A failure is logged to the PHP error log and retried after an hour (`backupplus_pitr_source_retry` transient). Capture keeps the old file until then. A connection file that is missing now produces an error asking for the PITR settings to be saved again.

It checks that `source_config` is the guarded `source.php` holding `DB_PASSWORD` and that `connection_file()` writes nothing to the work folder. It also checks that a saved `source.cnf` in the PITR folder is migrated and deleted, and that a CLI option file named `source.cnf` in another folder is kept. On a test site, the guard returned 404 over HTTP and the body held no password.

Upgrading does not change the database password. If `source.cnf` could have been read over HTTP, for example on nginx with a predictable backup directory name, change `DB_PASSWORD`.

### BPS-10: Unsalted hash of decrypted credentials is stored in backup history

**Severity:** Low. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `includes/class-incremental-backups.php:29`, `includes/core/trait-backup-boot.php:193-217,307`, `includes/core/trait-backup-completion.php:382`. Related: `includes/class-pitr-storage.php:62-66,108`, `includes/pitr/trait-state.php:132`.

**Description.** The incremental chain configuration fingerprint is `hash( 'sha256', serialize( [ site_url(), $configuration, $services, $instances, $credentials, ... ] ) )`. `$credentials` is the job `option_cache`, built from `BackupPlus_Options::get_backupplus_option()`, which returns decrypted provider settings (for example the FTP `pass`). PITR `settings_sha256` and the PITR fingerprint hash decrypted provider settings and connection options in the same way, but are stored only in the local PITR state file.

**Exploit scenario.** An attacker obtains an unencrypted database backup, which is the threat credential encryption is designed to address. Every other field in the serialized structure (host, user, path, instance IDs, site URL, exclusions, key directory) is readable in the same dump, so the attacker reconstructs it and runs an offline dictionary attack on the one unknown field. This is practical for a single destination with a human-chosen FTP, SFTP or WebDAV password and impractical for high-entropy API keys.

**Remediation criteria.**

* Fingerprints that need to change when credentials change are computed over the stored ciphertext envelopes, or with an HMAC keyed from the credential key ring, never over plaintext secrets.
* Existing history entries do not need rewriting, but the next full backup replaces the fingerprint.

**Resolution.** The incremental fingerprint is now computed over the stored ciphertext envelopes, the first option in the first criterion. Both criteria are met:

* `BackupPlus_Incremental_Backups::configuration()` replaces each `option_cache` entry that credential storage handles (`BackupPlus_Credential_Storage::handles()`) with its saved value. The saved value comes from the new `BackupPlus_Options::get_stored_backupplus_option()`, which `get_backupplus_option()` now also uses. Secret fields stay in their `bpcred:v1:` envelopes, and the other fields were already readable in the dump. The only other entries in the cache are the SSL flags and the public age recipients. An attacker with the dump therefore has no unknown plaintext to guess.
* `BackupPlus_Credential_Storage::keep()` already reuses an envelope when a setting is saved with the same credential under the active key. Saving settings therefore keeps the chain. Changing a credential or rotating the key re-encrypts the envelope, which changes the fingerprint, so the next backup is a full one.
* Existing history entries are not rewritten. They hold the old plaintext-derived hash, which no longer matches, so the first incremental backup after upgrading becomes a full backup. That backup records the new fingerprint.
* The PITR `settings_sha256` and chain fingerprint are unchanged. They are kept only in the local PITR state file in the backup directory, which no backup includes. Anyone who can read that file can also read `source.php`. Envelope hashes would change at every key rotation, which would block PITR recovery with "PITR storage settings changed" until a rescan.
* The external importer's resume state (`includes/class-sql-stream.php`) stored a SHA-256 of the whole target connection, password included. The hash now leaves the password out. A state saved with the previous hash is still accepted, so an interrupted import can resume after the upgrade.
* `scripts/check-incremental-backups.php` (`make test-wordpress`) saves an FTP destination through credential storage and checks four things. The password is saved as an envelope. The fingerprint ignores the decrypted values it is passed. Saving the same password again keeps the fingerprint. A new password changes it.

### BPS-11: Unauthenticated restore continuation relies on a weak job ID

**Severity:** Low. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `admin.php:102,104`, `includes/admin/trait-restore.php:140-153`, `includes/core/trait-backup-dispatch.php:25`, `includes/filesystem-functions/trait-files.php:26`.

**Description.** `wp_ajax_nopriv_backupplus_ajaxrestore_continue` is registered for unauthenticated users. It needs no nonce and no login; it checks only that the request's `job_id` equals the `backupplus_restore_in_progress` site option, using `!==` rather than `hash_equals()`. The job ID is `substr( md5( time() . wp_rand() ), 20 )`: 12 hex characters whose entropy is at most that of one `wp_rand()` call plus a guessable timestamp. The marker exists while a restore runs, and after a crashed restore until it is dismissed; the continuation path itself has no age limit.

A caller who knows the job ID can resume or replay the administrator's restore (including in parallel with the live one), receive the streamed restore log, and, with `backupplus_ajax_restore=continue_ajax_restore`, write arbitrary `hostname`, `username`, `password` and `connection_type` into the job's filesystem credentials, which are later loaded into `$_POST` for `WP_Filesystem`. On non-direct filesystems, the continuation page also prints a nonce for user ID 0, which is accepted by the unauthenticated `backupplus_ajaxrestore` path.

No unauthenticated leak of the job ID was found, and brute-forcing it online within a restore window is impractical, so this is Low. The same weak value names log files and backup archives.

The authenticated `backupplus_ajaxrestore` path relies on the nonce alone and has no `user_can_manage()` check, unlike the `backupplus_ajax` dispatcher. `downloadlatestmodlog` (`includes/core/trait-wordpress-hooks.php:97`) likewise checks only a nonce. Neither is exploitable while nonces are only issued to managers.

**Remediation criteria.**

* Restore continuation uses a separate `random_bytes( 32 )` token, stored hashed, compared with `hash_equals()`, and expiring after a fixed period.
* The continuation path does not accept filesystem credentials; they can only be supplied by an authenticated manager.
* `backupplus_ajaxrestore` and `downloadlatestmodlog` check `user_can_manage()` in addition to the nonce.
* Job and backup nonces are generated from `random_bytes()`.

**Resolution.** `includes/class-restore-continuation.php` (`BackupPlus_Restore_Continuation`) holds the continuation secret. Every criterion above is met:

* `prepare_ajax_restore()` renders the restore page, which only a manager reaches. It calls `issue()` for the job, which makes a token from `random_bytes( 32 )` and gives it to the page as a hidden field. The `backupplus_restore_continuation` site option keeps the SHA-256 hash of the token, the job ID and an expiry time 24 hours later. That is the period during which the "Unfinished restoration" notice is shown. The token itself is not stored. A new token replaces the previous one, so continuing from the notice issues a fresh token. The page script sends the token in the POST body of every `backupplus_ajaxrestore_continue` request. `prepare_restore()` checks it with `verify()` before the job is loaded or its log opened. `verify()` requires a 64-character hexadecimal token, compares the job ID with both the restore in progress and the token's job, and the hash, with `hash_equals()`, and refuses an expired token. A refused request ends without output, as before. A token in the query string is ignored. The option is carried over a database restore with `backupplus_restore_in_progress`, through the configuration bundle, because the restored users table can end the session that started the restore. On a multisite network the in-progress marker and the continuation option are network options in `wp_sitemeta`, which a network restore replaces. The bundle now keeps both there too, and `restore_network_bundle()` puts them back after `sitemeta` is restored (`includes/restorer/trait-database-sql.php`). The job data, kept in the same table, is also written back from memory as soon as the table is swapped in (`save_job_state()` in `includes/restorer/trait-database-tables.php`; on a single site, after `wp_options`). Before, it existed only in memory until the next table began, so a request ended in between left a continuation with no job to resume (`job_id_nojobdata`). It is removed when the restore finishes or is dismissed. It is excluded from the settings keys, so it is neither exported nor accepted by a settings save.
* The continuation action accepts only `backupplus_ajax_restore=do_ajax_restore`, which runs the saved job. It can no longer start a restore page (`start_ajax_restore`) or save filesystem credentials (`continue_ajax_restore`). Filesystem credentials are also saved only for a request from a user who passes `user_can_manage()`, and only string values are taken.
* `backupplus_ajaxrestore` is no longer registered for logged-out requests, and requires `user_can_manage()` as well as the nonce. A nonce made for user ID 0 by the filesystem credentials form is therefore useless. `downloadlatestmodlog` requires `user_can_manage()` as well as the nonce.
* `backup_time_nonce()` makes job IDs with `bin2hex( random_bytes( 6 ) )`: 12 hexadecimal characters as before, which backup file names expect, but 48 random bits, instead of `md5( time() . wp_rand() )`.
* `tests/Unit/Restore/RestoreContinuationTest.php` checks the token format, that only its hash is stored, the expiry, and that a new token replaces the old one. It checks that a token is refused for another job, when no restore is in progress, and when the token is malformed, is the stored hash, or the stored value is damaged. It also checks that `clear()` removes only the given job's token, the job ID format and its uniqueness within one second, and that only the continuation action is registered for logged-out requests. `scripts/check-restore-continuation.php` (`make test-wordpress`) sends logged-out requests to `admin-ajax.php`. It checks that a continuation is refused without output and without creating job data or a log in each of these cases: without the token, with another token, with the stored hash, with the token in the URL, for another restore in progress, with an expired token, with `start_ajax_restore`, and with filesystem credentials. It also checks that the issued token does continue the restore. It then checks that `backupplus_ajaxrestore` has no handler for logged-out requests. For a subscriber with valid nonces of their own, it checks that `backupplus_ajaxrestore` and `downloadlatestmodlog` are refused, and that an administrator still downloads the latest log. Against the code before this fix, the script fails on its first case, because the job ID alone continued the restore. `scripts/check-interrupted-restore-continuation.php` runs a real restore over HTTP, on a single site (`make test-wordpress`) and on both networks of `dev/test-sites.sh` (through `scripts/integration/check-multisite.php`). An administrator whose session began after the backup starts a database restore as the restore dialog does. A temporary must-use plugin ends that request just after the table holding the restore state is swapped in: `wp_options`, or on a network `wp_sitemeta`, which comes after `wp_users` and `wp_usermeta` in the dump. A logged-out continuation with the page's token must then finish the restore. On a network the check fails with the continuation refused when `restore_network_bundle()` is removed, and on both kinds of site with `job_id_nojobdata` when `save_job_state()` is removed. WordPress keeps maintenance mode on for 10 minutes after a restore that dies, and answers every request, admin-ajax.php included, with 503 until then; the check moves that start back instead of waiting.

### BPS-12: PHP database dumper escaping ignores the connection charset

**Severity:** Low. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `includes/backup/trait-database-tables.php:674`, `includes/database-utility/trait-statements.php:18-140`.

**Description.** The PHP dumper escapes string values with `str_replace()` of `\` and `'`. This is correct for utf8, utf8mb4 and latin1, but in GBK, GB18030, Big5, SJIS and CP932 the byte 0x5C (`\`) can be the second byte of a two-byte character. A stored value ending in such a character is written as `...\x81\x5C\x5C'`; on restore the server reads `\x81\x5C` as one character and `\'` as an escaped quote, so the string does not terminate and the next attacker-controlled value is parsed as SQL. Stacked queries are not possible (`mysqli_query`), but extra rows can be injected into the same `INSERT`, for example into `usermeta` capabilities. A `SET NAMES gbk` header on a utf8mb4 dump triggers the same re-pairing. The restore-side statement splitter is byte-based in the same way. The same multibyte issue applies in principle to `%i` identifier quoting in `includes/class-sql.php:124-130`, but no path was found where a low-privileged user controls an identifier.

**Exploit scenario.** On a site whose `DB_CHARSET` is one of the affected charsets, a commenter or subscriber stores a crafted value; a later restore of that backup runs attacker-chosen SQL as the WordPress database user.

**Remediation criteria.**

* String values are escaped with `mysqli_real_escape_string()` on the dump connection, or values containing bytes ≥ 0x80 are written as hex literals.
* Alternatively, dump and restore refuse to run when the connection charset is one where 0x5C or 0x60 can be a trail byte.
* `%i` rejects identifiers containing bytes ≥ 0x80 unless the connection charset is utf8, utf8mb4, latin1 or ascii.

**Resolution.** The first and third criteria are met; the second is not needed.

* `BackupPlus_SQL::quote()` (`includes/class-sql.php`) makes the literal for every string value that the PHP dumper writes (`includes/backup/trait-database-tables.php`). It escapes with `mysqli_real_escape_string()` on the dump connection, which knows the connection character set, instead of `str_replace()` of `\` and `'`. Under GBK, GB18030, Big5, SJIS and CP932, where 0x5C can be the second byte of a character, a value with a byte of 0x80 or more is written as a hexadecimal literal with a character set introducer, for example `_gbk 0x...`. No character in such a literal can pair with a quote, and the byte-based statement splitter on restore cannot misread it. Values with only ASCII bytes, and all values on other character sets, stay readable text. `NO_BACKSLASH_ESCAPES`, which would change what the library escapes, is already removed from the dump session by `set_sql_mode()`.
* The dump header names the character set of the connection that read and escaped the values (`BackupPlus_SQL::charset()`), not the one WordPress would choose by configuration, so that the `SET NAMES` line and the escaping agree.
* `BackupPlus_SQL::identifier()` (`%i`) refuses a name with a byte of 0x80 or more once a connection of this request has used one of those five character sets, whether at connection time or through a `SET NAMES` statement run by `script()`. The check is a request-wide flag that is never reset, so it fails closed. A non-ASCII table name on such a site is therefore refused, as the criteria allow.
* `scripts/check-dump-escaping.php` (`make test-wordpress`) connects to the site's database with each of utf8mb4, GBK, Big5, SJIS, CP932 and, where the server has it, GB18030. It runs the literals from `quote()` as an `INSERT` and checks that the rows read back are the values, byte for byte. The values include one ending in a character whose second byte is a backslash, one made of two of them, quotes, NUL, line breaks and the value that an attacker would store to add a row. It checks that no row is injected. It runs the previous escaping on the same values and requires it to fail on the multibyte character sets. It then checks that `%i` refuses bytes of 0x80 or more after those connections and that it accepts non-ASCII names on utf8mb4 before them. The dump of a database through the PHP dumper was run on the development site and completed without errors. The restore side was not changed: a `SET NAMES` line of a foreign dump still runs as written when the server supports the character set, so a foreign dump made for GBK is read as GBK, as it was meant.
* The mysqldump path (`backup_table_bindump()`) now passes `--default-character-set` with the dump connection's character set, so mysqldump does not escape for a different one. It falls back to the PHP dumper when that character set is not a plain name or is one of the five above, and when the database or table name starts with `-`, which mysqldump could read as an option.

### BPS-18: External database import guard can be bypassed

**Severity:** Low. **Status:** Fixed. **Confirmed.** The locations below refer to the code as reviewed.

**Location:** `includes/class-sql-stream.php:95`.

**Description.** External database restore blocks statements beginning with `CREATE|DROP|ALTER DATABASE` or `USE`. Statements with qualified names (`DROP TABLE otherdb.t`, `INSERT INTO otherdb.x`), a leading comment (`/* */ USE x`) or executable comments are not blocked and run on the target connection.

**Exploit scenario.** A tampered external-database dump modifies other schemas reachable by the target account.

**Remediation criteria.**

* Leading comments are stripped before the check, executable comments are rejected or evaluated, and qualified references to another schema are rejected; or the target account is documented as needing access to only the target schema, and the guard is described as a convenience rather than a boundary.

**Resolution.** Both alternatives are implemented. `BackupPlus_External_Importer::restore()` (`includes/class-sql-stream.php`) passes every statement to `BackupPlus_External_SQL_Guard` (`includes/class-external-sql-guard.php`) before running it, and `docs/external-databases.md` documents the target account's grants as the boundary:

* Comments are dropped wherever they appear in the statement, not only at its start. A version that MySQL (five digits) and MariaDB (five or six) would read differently is refused if either reading would run. Comments nested in an executable comment, and line comments inside one, are refused.
* Quotes are read under the session's `ANSI_QUOTES` and `NO_BACKSLASH_ESCAPES`. Both, and the client character set, are read from the server when the restore starts and after every `SET`. A character set whose multibyte characters can end in a backslash byte stops the restore.
* A name qualified with any schema the account can see (`information_schema.SCHEMATA`) other than the target is refused anywhere in the statement, including bodies and view definitions. Qualified names are compared case-insensitively, and whitespace or comments around the dot do not hide them. Comparing against the visible schemas, rather than refusing every qualified name, keeps `table.column` references in views and triggers working.
* Only the statements the PHP exporter, `mysqldump` and `mariadb-dump` write are run: session `SET`, `INSERT`, `REPLACE`, `LOCK`/`UNLOCK TABLES`, `ALTER TABLE`, `COMMIT`, and `CREATE`/`DROP` of tables, views, triggers, procedures and functions. `CREATE` modifiers (`OR REPLACE`, `ALGORITHM`, `DEFINER`, `SQL SECURITY`) are parsed so that a non-reserved word used as a definer cannot hide `CREATE USER`. `PREPARE`/`EXECUTE`, which could build a name from strings, global and persisted variables, `SET STATEMENT … FOR`, events, `LOAD_FILE`, `INTO OUTFILE`/`DUMPFILE` and a second statement are refused. So are table options and session settings that reach outside the schema: the FEDERATED, FederatedX, CONNECT and SPIDER engines (as a table or partition option, through `default_storage_engine`, or as a quoted name), `CONNECTION`, `DATA DIRECTORY` and `INDEX DIRECTORY`, `sql_log_bin` set to anything but off or a saved value, and replication and debugging internals such as `gtid_next` and `pseudo_thread_id`. The restore refuses to start when `MYSQL_CLIENT_FLAGS` enables multiple statements.
* `tests/Unit/Backup/ExternalSqlGuardTest.php` covers each bypass in the description and the variants above, and real exporter, `mysqldump` and `mariadb-dump` statements that must pass. `scripts/check-backup-sources.php` checks, in WordPress and as the site's account, that tampered dumps are refused before the statement runs and that nothing after it runs. The grants in `docs/external-databases.md` were checked on MariaDB 11.8: an account holding only them exported and restored tables with a foreign key, a view, a trigger and routines with both exporters.

Statements before a refused one have already run, and the guard limited them to the target schema. The restore stops at the refused statement.

### BPS-19: SQL lint gaps

**Severity:** Info. **Status:** Fixed. The locations below refer to the code as reviewed.

**Location:** `scripts/check-sql.php`.

**Description.** The repository passes the lint, and no SQL injection was found in current code: `BackupPlus_SQL` binds `?` values with real server-side `mysqli_prepare()`, and `%i`, `%a` and `%d` are validated. The lint, however, would not catch several ways of reintroducing concatenated SQL. Each of the following was confirmed to pass the lint with a sample file, except fragment forgery, which was noted from the code:

* Concatenation split across statements into an executor: `$q = 'DELETE FROM '; $q .= $t; $x->script( $q );`. The adjacency check (around line 124) only flags a keyword literal directly beside `.`, and any method named `script` or `sql_exec` on any object accepts any variable (around line 118).
* Lowercase keywords: the concatenation keyword check (around line 131) has no `/i` flag.
* Keywords missing from the list (around line 44): `WITH`, `EXPLAIN`, `DO`, `LOAD`, `HANDLER`, `PREPARE`, `EXECUTE`, `FLUSH`, `OPTIMIZE`, `ANALYZE`, `BEGIN`, `START`, `XA`.
* Literals that do not start with a keyword: `' WHERE id = ' . $t`, `'/*!40101 SET NAMES ' . ...` (`includes/backup/trait-database.php:930`), `'--execute=' . $sql`.
* Static calls: fully qualified `\BackupPlus_SQL::fragment( $t )` (PHP 8 `T_NAME_FULLY_QUALIFIED`), `self::`, `static::`, and static calls on other classes (around lines 99-100). Plain functions are checked only when their name starts with `mysql` (around line 113).
* Dynamic calls: `$wpdb->$m( ... )`, `call_user_func()`, `array( $wpdb, 'query' )`.
* Unlisted sinks: `mysqli::real_query()`, `mysqli::multi_query()`, `mysqli::send_query()`, `PDO::exec()`, and `$wpdb->insert/update/delete/replace` (which interpolate the table name; current uses in `includes/restorer/trait-database-tables.php:598,611` use the plugin's own prefix).
* Other builders: `implode()`, `strtr()`, `str_replace()`, `sprintf()` with a non-literal format.
* Fragment forgery: only `new BackupPlus_SQL_Fragment` is detected; `new $cls`, Reflection and unserialization are not, and the constructor is public.

If a site defines `MYSQL_CLIENT_FLAGS` with `MYSQLI_CLIENT_MULTI_STATEMENTS`, WordPress's connection would execute stacked statements; `BackupPlus_SQL` could detect this and refuse.

**Remediation criteria.**

* The lint tracks string variables assigned from SQL-keyword literals through `.=` and flags them when passed to an executor; matches keywords case-insensitively; flags any literal containing a SQL keyword at a token boundary that is concatenated with a variable; resolves `\`, `self::` and `static::` static calls; flags dynamic calls on `$wpdb` and `mysqli` objects; and includes the listed sinks.
* `BackupPlus_SQL_Fragment` can only be constructed by `BackupPlus_SQL` (private constructor and a named factory).
* Each pattern above has a negative fixture in the lint's tests.

**Resolution.** `scripts/check-sql.php` is now a token-level check (`BackupPlus_SQL_Check`) that follows `.` chains, variables and calls, and `BackupPlus_SQL_Fragment` can no longer be made outside `BackupPlus_SQL`. No exemption was added for plugin code: what the stricter check reported was changed (see below). The criteria are met as follows:

* **Variables.** Within each function, the check records which variables and `$this` properties hold SQL text, either assigned from text that contains SQL or copied from such a variable. Appending a non-constant to one with `.=` is reported. The variable then counts as assembled SQL, and passing it to `script()` or `sql_exec()` is reported too. Executors still take a plain variable that holds a dump statement.
* **Keywords.** Text counts as SQL when it contains a statement or clause keyword in capitals at a token boundary, or SQL syntax in any case. The keyword list now includes `WITH`, `EXPLAIN`, `DO`, `LOAD`, `HANDLER`, `PREPARE`, `EXECUTE`, `FLUSH`, `OPTIMIZE`, `ANALYZE`, `BEGIN`, `START`, `XA` and other statements, plus clause words such as `WHERE`, `FROM`, `VALUES`, `ORDER BY`, `NAMES` and `COLLATE`. The syntax patterns include `delete from`, `insert … into`, `update … set`, `select * from`, `where id =`, `set names`, `/*!40101` and `--execute=`. A single lowercase word on its own is not taken for SQL, because `'Delete ' . $file` is an ordinary log message, so keywords match case-insensitively only as part of SQL syntax.
* **Any literal.** Every `.` chain, interpolated string and heredoc is checked as a whole, wherever the SQL appears in it. That covers `' WHERE id = ' . $t`, `$t . ' ORDER BY id'`, `'/*!40101 SET NAMES ' . $charset` and `'--execute=' . $sql`. A constant that the same file defines counts as its text. A regular expression is not SQL: neither the first argument of a `preg_*()` function nor text containing `(?:`, `\s`, `\A` or similar syntax is checked. A sink-named wrapper may hand its own SQL parameter to a native client as `'--execute=' . $sql` (`BackupPlus_PITR_Database::query()`), just as it may pass that parameter to a sink.
* **Static calls.** `\Name` is resolved, including PHP 8's `T_NAME_FULLY_QUALIFIED`, and `self::`, `static::` and `parent::` resolve to the enclosing class or its parent. Static calls with a sink name are checked on `BackupPlus_SQL` and on any class whose name has an `SQL`, `DB`, `Database`, `WPDB` or `Mysqli` part. Other classes' static `query()`, `prepare()` and `render()` build HTTP queries or templates. Function sinks are checked when fully qualified (`\mysqli_query()`).
* **Dynamic calls.** A method call by a computed name (`->$m()`, `->{$m}()`, `::$m()`) is reported on any object; the plugin had none. A callable that names an SQL function (`'mysqli_query'`, `'wpdb::query'`) or an SQL method (`array( $wpdb, $m )`, `array( $db, 'query' )`, `array( 'BackupPlus_SQL', 'fragment' )`) is reported, so `call_user_func()` cannot reach one. `function_exists( 'mysqli_query' )` is allowed.
* **Sinks.** `real_query()`, `multi_query()`, `send_query()`, `mysqli_real_query()`, `mysqli_multi_query()`, `mysqli_send_query()` and `mysqli_stmt_prepare()` are sinks, and so is `exec()` on a database receiver (`PDO::exec()`, but not phpseclib's SSH `exec()`). `$wpdb->insert()`, `update()`, `delete()` and `replace()` are reported. The two uses in `includes/restorer/trait-database-tables.php` now run `UPDATE %i SET option_value = ? WHERE option_name = ?` through `BackupPlus_SQL`.
* **Builders.** `implode()`, `join()`, `strtr()`, `str_replace()`, `str_ireplace()` and `substr_replace()` are reported when any argument contains SQL text or holds it in a variable. `sprintf()` and `vsprintf()` are reported when the format does, including a format held in a variable. Their other arguments are values, such as a statement named in an error message.
* **Later additions.** `mysqli_execute_query()` and `execute_query()` are sinks, as is `MYSQLI_INIT_COMMAND` passed to `mysqli_options()` or `options()`. A variable holding SQL is reported when it is interpolated into a string, passed as any `sprintf()`/`vsprintf()` argument, or used as the replacement or subject of `preg_replace()`/`preg_replace_callback()`; a non-constant replacement into SQL text is reported too. An array filled element by element (`$parts[] = …`) holds SQL when any element does. `tests/Support/check-sql/fail/review-gaps.inc` and `pass/review-gaps.inc` cover these.
* **Fragments.** `BackupPlus_SQL_Fragment` has a private constructor, which `BackupPlus_SQL::fragment()` reaches through a closure bound to the class. `__wakeup()` and `__unserialize()` throw, and `compile()` refuses a fragment without compiled text, such as one made by `ReflectionClass::newInstanceWithoutConstructor()`. The check reports any mention of the class name outside `instanceof` and type declarations, including in strings, which covers `new $class`, `new ReflectionClass( … )` and serialized payloads.
* **Tests.** `tests/Unit/Sql/SqlConstructionCheckTest.php` runs the check on every fixture in `tests/Support/check-sql/fail` and asserts that it reports exactly the lines each fixture marks. There is at least one fixture per pattern group in the description: 90 marked lines, of which the previous check caught 8. It also runs the fixtures in `tests/Support/check-sql/pass`, which must produce no reports. These cover templates, dump writing and text that mentions SQL but is not SQL: log messages, MIME types, regular expressions and hook callbacks. A final test checks that the plugin passes. `tests/Unit/Sql/SqlFragmentTest.php` covers the private constructor, unserialization and Reflection.

The plugin changes made to pass the stricter check:

* The PHP dump header writes `/*!40101 SET NAMES %i */` through `BackupPlus_SQL::render()`. The restorer and the dump analyser accept the quoted name as well as the unquoted one in older dumps (`includes/restorer/trait-database-restore.php`, `includes/core/trait-database-analysis.php`).
* The restorer's table-option rewrites (`prepare_create_table()`) search for the dump's own matched text. The replacement character sets and collations are rendered as `CHARACTER SET %i COLLATE %i`, `COLLATE=%i` and `COLLATE %i`, and the engine fallback replaces the matched `ENGINE=` text. These quoted forms, and `SET NAMES` with a quoted name, were checked on MySQL 8.4, MariaDB 10.11 and MariaDB 11.4.
* PITR replay replaces an account-control statement with `BackupPlus_SQL::render( 'DO 0' )`, padded to the same length (`includes/class-pitr-binlog.php`).
* Messages that joined capitalised SQL with a value were reworded. These were the no-tables backup log line, the dump comment for an unreadable table definition, the PITR isolation grant hint, the restore `SET NAMES` notices, and the PITR SQL guard's refusal of `SET PASSWORD`-style statements (which now uses its usual statement description). The restore notice `Found SET NAMES %1$s, …` is translatable, so its existing translations fall back to English until the language files are regenerated.

`tests/` is skipped by the check, like `scripts/` and `dev/`, because test code builds SQL fixtures (for example `self::HEAD . $sql` in `tests/Unit/Pitr/PitrSqlGuardTest.php`). Those directories were outside this review's scope.

The description's suggestion that `BackupPlus_SQL` refuse a connection opened with `MYSQLI_CLIENT_MULTI_STATEMENTS` is not part of the criteria and was not implemented here. The external database importer already refuses that flag (BPS-18).

### BPS-20: Hardening notes

**Severity:** Info. **Status:** Fixed. The locations below refer to the code as reviewed.

These are not vulnerabilities on their own, but several make the findings above worse or could become findings if the surrounding code changes.

* **Decrypted secrets in admin HTML.** `includes/class-storage-methods-interface.php:55-70` sends decrypted instance settings to the browser, and templates render them as `value="{{secretkey}}"`, `{{pass}}` and so on (for example `methods/s3/base.php:1220`, `includes/class-remote-storage-module.php:181`). Only Dropbox and Google Drive override `filter_frontend_settings_keys()`. Advanced Tools "Options (raw)" (`includes/admin/trait-existing-backups.php:908-913`) prints every option decrypted except PITR credentials, and raw backup info prints decrypted job data. Any admin XSS (BPS-04) therefore yields every remote credential. Write-only placeholders would remove this.
* **`phpinfo` diagnostics** (`includes/wpadmin-commands/trait-diagnostics.php:78-105`) dump environment variables and every defined constant, including `DB_PASSWORD`, the salts and an environment-supplied `BACKUPPLUS_CREDENTIAL_KEYS`.
* **Administrator power tools.** `call_wordpress_action` runs an arbitrary `do_action_ref_array()` with JSON arguments (`includes/admin/trait-ajax.php:464-522`); `backupplus_broadcastaction` runs an arbitrary `do_action()` (`includes/admin/trait-settings-page.php:61-69`); `httpget` is an SSRF tool that returns the full response and skips `wp_http_validate_url()` whenever the plugins directory is writable (`includes/admin/trait-http.php:36-121`). All need a manager and a nonce; they matter on sites where administrators are deliberately restricted.
* **Unused server-side decrypt endpoint.** `admin_post_backupplus_decrypt_database` (`includes/class-database-encryption.php:178-205`) accepts an age private identity and passphrase over POST. It is capability-, nonce- and POST-protected, but no interface uses it (only `scripts/check-age-encryption.php`), and `docs/database-backup-encryption.md` says private keys never reach the server. Consider removing it.
* **Legacy Rijndael format.** The UpdraftPlus format (zero IV, no MAC, raw passphrase truncated at 32 bytes) is still decrypted server-side using the stored `backupplus_encryptionphrase` (`includes/class-backupplus-crypto.php:18-24`, `includes/class-backupplus-encryption.php:168-205`, `includes/restorer/trait-unpack.php:308-316`), contrary to `docs/database-backup-encryption.md`, which directs legacy archives to the Extract tab. There is no downgrade from age: `decrypt_stream` dispatches on the `age-encryption.org/` prefix and never falls back.
* **Credential key retirement.** Rotation keeps every historical key (`includes/class-credential-key-store.php:706`), so the current key file decrypts every credential ever written. This is documented; a retirement command would limit it.
* **age archives are not bound to their name or backup set.** A remote-storage attacker can swap or roll back archives; this is caught only where local history checksums exist.
* **Plaintext transports.** FTP defaults to `encryption => 'none'` (`methods/ftp.php:54`); WebDAV accepts `http://` with Basic or Digest authentication (`methods/webdav/client.php:120`); ntfy accepts an `http` server and sends its bearer token over it (`includes/class-ntfy.php:29`). S3-generic configurations created before `signature_version` existed default to SigV2 (`methods/s3generic.php:187`). ntfy reports go to public `ntfy.sh` by default, protected only by the topic name.
* **Incremental deletion and symlinks.** `includes/restorer/trait-entity-restore.php:446-460` checks parents for symlinks but not the target; a pre-existing symlink to a directory is followed by `WP_Filesystem_Direct::delete( $path, true )`.
* **Zip browser extraction** (`includes/wpadmin-commands/trait-jstree.php:323-324`) extracts to `extract-<hex>-<original name>`, keeping `.php`, and deletes it only when the second download stage runs.
* **Decompression.** The zip disk-space check only runs under cron (`includes/filesystem-functions/trait-unzip.php:398`); zstd is correctly capped.
* **Shell values from configuration.** `DB_NAME` (`includes/core/trait-binaries.php:90`), `BACKUPPLUS_DIR` (`includes/core/trait-environment.php:50`) and `BACKUPPLUS_BINZIP_OPTS` (`includes/class-zip.php:484`) are interpolated into shell commands unescaped. They come from server configuration, not users. `zip -@` reads newline-separated names on standard input (`includes/class-zip.php:533`), so a file name containing a newline could add another path to an archive.
* **Template includes.** `extract( $extract_these )` runs before `include $template_file` (`includes/admin/trait-templates.php:81-83`); a key named `template_file` would redirect the include. No caller passes one; `EXTR_SKIP` would prevent it.
* **Range handling.** For `bytes=-N` the partial file servlet sends N+1 bytes and the start position can go negative (`includes/class-partialfileservlet.php`, `getStartPosition()`); there is no out-of-bounds read.
* **Binary discovery.** `native_directory()` (`includes/class-pitr-admin.php:204-216`) takes candidates from the PHP process `PATH`, which could contain relative or writable entries.
* **`.htaccess` syntax.** Protection files use Apache 2.2 `deny from all`; on Apache 2.4 without `mod_access_compat` this yields a 500, which still denies access.
* **Minor defects that fail closed.** `includes/admin/trait-ajax.php:159` compares `'backupplus_'` with an 8-character substring, so the `doaction` branch is unreachable; do not "fix" it without adding a capability check. `includes/backup-module/trait-authentication.php:70,119` read `BackupPlus_<id>auth` while links send `backupplus_<id>auth`, so those nonce-checked authorization links never fire (fixed with BPS-01). `includes/admin/trait-restore.php:87-94` clears the restore marker on `action=backupplus_restore_abort&job_id=` without a nonce. `.tar` and `.tar.gz` restore requires `includes/PEAR/Archive/Tar.php`, which is missing. `get_outgoing_ip_address()` (`includes/core/trait-http.php:66`) and `methods/pcloud/BackupPlus_Pcloud_API.php` are unused.

**Resolution.** Each note is resolved as follows. Where a note left a choice open, the maintainers chose: remove all three power tools, keep server-side decryption of legacy databases and correct the documentation, add a key retirement command, and keep plaintext transports working with safe defaults and warnings rather than refusing them.

* **Decrypted secrets in admin HTML.** Saved secrets reach the browser only as a fixed placeholder (`BackupPlus_Credential_Storage::PLACEHOLDER`), never decrypted. `BackupPlus_Credential_Storage::mask()` replaces every non-empty field that `secret_fields()` names (the same list that decides what is encrypted) and is applied to the storage instances sent to the settings templates (`includes/class-storage-methods-interface.php`; the `default` template of a new instance comes from the code), the external database connections (`includes/class-sources-admin.php`), the ntfy topic and token (`templates/wp-admin/settings/form-contents.php`), every credential option in Advanced Tools → Options (raw), and the credentials in the job data of raw backup info (`mask_job()`; `includes/admin/trait-existing-backups.php`). Fields a template derives from a secret, such as the parts of a legacy WebDAV URL, are masked as shown. On save, `incoming()` puts the saved value back wherever the form returns the placeholder at the same path, which includes the instance ID, so an unchanged secret keeps its envelope and the incremental fingerprint (BPS-10) does not change. A placeholder with nothing saved behind it is saved empty, and the placeholder itself is never stored. Connection tests send the instance ID, and `do_credentials_test()` substitutes that instance's saved secrets (`unmask_at()`). `tests/Unit/Credentials/CredentialPlaceholderTest.php` covers every provider's secret fields: placeholders on the page, unchanged envelopes after a save with placeholders, replacing and clearing a secret, a placeholder without a saved secret, structured and whole-value secrets, unreadable saved secrets, connection tests that get only their own instance's secrets, and masked job data with readable progress. A saved secret is put back only while the destination is unchanged. When a save or connection test changes a field that says where the secret goes (`endpoint_fields()`: host, port, server, endpoint, account, protocol, TLS and host-key settings; filterable), the placeholders of that instance are taken as empty, so the stored password cannot be sent to a server of the submitter's choosing. The settings save response masks credential options as well. The flat credential options of older versions (`s3_pass`, `dropboxtk_access_token` and others) are no longer settings keys, and the upgrade deletes them (`BackupPlus_Legacy_Compatibility::delete_flat_credential_options()`).
* **`phpinfo` diagnostics.** `phpinfo()` runs without its Environment and PHP Variables sections, and `BackupPlus_Diagnostics_Redaction` (`includes/class-diagnostics-redaction.php`) redacts the rest: rows and constants whose name looks like a secret (`DB_PASSWORD`, the keys and salts, `BACKUPPLUS_CREDENTIAL_KEYS`, `*PASSWORD*`, `*SECRET*`, `*TOKEN*` and similar) show `***`, the request-environment sections that mod_php adds are removed, credentials in URLs and query strings (such as a `session.save_path` with `?auth=`) are masked, and the values of secret constants, environment and server variables and ini directives are masked wherever else they appear. Array constants are shown with their secret entries masked, and licence keys (`newrelic.license` and similar) count as secrets. `tests/Unit/Backup/DiagnosticsRedactionTest.php` covers the names, the constants, the HTML and text forms of `phpinfo()` and escaped values.
* **Administrator power tools.** Removed. The `call_wordpress_action` command, `call_wp_action()`, the `httpget` subaction and `includes/admin/trait-http.php`, their debug-console rows and their JavaScript are gone. The generic `backupplus_broadcastaction`, which ran any action the request named, is replaced by a fixed `backupplus_searchreplace` action that runs only the search / replace hook, for a manager, with the nonce, sent by POST (`includes/admin/trait-settings-page.php`). The unreachable `doaction` branch of the AJAX handler (`includes/admin/trait-ajax.php:159`) is removed rather than repaired. `tests/Unit/Backup/AdminHardeningTest.php` checks that no shipped source offers these tools.
* **Unused server-side decrypt endpoint.** Removed with its handler (`includes/class-database-encryption.php`). `scripts/check-age-encryption.php` now exercises the decryption that restore and the CLI use directly, and checks over HTTP that `admin-post.php` has no handler for the old action and returns neither plaintext nor the supplied secrets.
* **Legacy Rijndael format.** Server-side decryption is kept, and `docs/database-backup-encryption.md` now describes it: restore preflight and database unpack decrypt a legacy database with the saved or job-supplied phrase into a private temporary file that is removed afterwards (BPS-14); `wp backupplus restore` decrypts legacy archives of any kind; legacy file archives restored from the browser go through the Extract tab. It also states that the format is unauthenticated and that there is no downgrade from age.
* **Credential key retirement.** `wp backupplus credential-keys retire` (`includes/class-cli.php`, `BackupPlus_Credential_Key_Rotation::retire_manually()`) re-encrypts, on every site of the network, whatever an older key wrote: provider settings, other credential options, saved job credentials, provider settings inside saved job snapshots (through the `backupplus_credentials_job_snapshot` filter), and, through the new `backupplus_credentials_retire` hook, Dropbox tokens and pending PKCE verifiers (`BackupPlus_Dropbox_Token_Migration::retire()`). Envelopes of the active key are left unchanged. `BackupPlus_Credential_Key_Store::retire()` then removes every other key under the key file lock, and only if `BackupPlus_Credential_Storage::key_references()` finds no envelope of those keys in any option of any site or in any network option; otherwise it names the places and changes nothing. The command warns that older backups and recovery-key downloads can no longer be decrypted, and asks for confirmation unless `--yes` is given. For environment-managed keys it re-encrypts the database in the same way and prints the key-ring value with only the active key. `scripts/check-credential-key-retirement.php`, run by `scripts/check-dropbox-token-storage.php`, covers re-encryption of an old Dropbox token, PKCE verifier and job snapshot, including a Dropbox token inside the snapshot, unchanged current envelopes, the refusal while a copy of an old envelope remains elsewhere, removal of the old keys and a repeated retirement. Without the Dropbox hook it fails with that refusal. The environment-key path is not run by a test, because the key ring is read when the plugin loads.
* **age archives are not bound to their name or backup set.** The format is unchanged, but web restore now refuses an encrypted archive whose SHA-256 differs from the checksum the local history recorded for it (`BackupPlus_Age_Restore::manifest()`, `BackupPlus_Archive_Checksum_Exception`), before anything is transferred; `wp backupplus restore` already checked recorded checksums. Backups known only from a rescan have no checksums and are restored as before. `docs/database-backup-encryption.md` documents what is and is not protected, and recommends keeping history and versioned or object-locked buckets. `tests/Unit/Age/AgeRestoreTest.php` covers a matching, a swapped and an unrecorded archive.
* **Plaintext transports.** New FTP destinations default to FTPS (explicit TLS). Destinations saved before the setting existed keep plain FTP, as they have always connected (`methods/ftp.php`), and `wp backupplus remote set` now starts new instances from the provider defaults. WebDAV over `http://` and ntfy over `http://` keep working. Plain FTP, WebDAV over HTTP and ntfy over HTTP show a warning beside the setting, and each connection adds a line to the backup log, without the password, token or topic. S3-compatible destinations without a saved signature version now use SigV4 and log that they do; an explicit SigV2 is kept. DreamObjects always uses SigV4. The ntfy settings and `docs/notifications.md` explain that a topic on the public `ntfy.sh` is the only protection, and suggest a random topic, which is not saved unless entered. `docs/cloud-providers.md` documents the defaults. `tests/Unit/Providers/FtpTest.php`, `WebDavTest.php`, `NtfyTest.php` and `S3Test.php` cover the defaults, the kept legacy values, the warnings and the log lines.
* **Incremental deletion and symlinks.** Every deletion a restore makes goes through `BackupPlus_Filesystem_Functions::delete_restore_path()` (`includes/filesystem-functions/trait-files.php`), which removes a link as a link and, on the direct filesystem, walks folders without following links. That covers incremental deletions and the scan for them, overwriting without a backup, the `-old` folder and the folder being replaced (`includes/restorer/trait-entity-restore.php`, `trait-file-restore.php`). `remove_local_directory()` also removes links instead of following them. On FTP and SSH filesystems, deletion is left to `WP_Filesystem`, which cannot tell a link from a folder in every case. `scripts/check-incremental-restore.php` deletes a link to a folder, a folder holding such a link, and an old folder holding one, and checks that the files the links point to survive. On the previous code it fails.
* **Zip browser extraction.** A file the zip browser extracts is written as `extract-<128 random bits>.tmp`, so no web server runs it whatever the entry is called. The entry's name is kept for that user only and used only for the download's `Content-Disposition` (`includes/wpadmin-commands/trait-jstree.php`, `spool_file()`, `BackupPlus_PartialFileServlet::sendFile()`). Not in the note, but the same code: the download handler's `filepath` accepted any file in the backup directory, which stage 2 then sent and deleted and the `delete` stage deleted. It now accepts only an extraction of the current user (`includes/admin/trait-downloads.php`), which stage 2 removes in a `finally` block with `ignore_user_abort( true )`. The temporary file cleanup removes an abandoned extraction after 12 hours, as it does every `.tmp` file. `scripts/check-zip-browser-download.php` extracts a `.php` entry and checks the random name and content, that another backup file or another user's extraction is refused and left in place, and that the user's own extraction can be removed. The extraction needs twice the entry's size free on disk, copies at most the size the archive declares, and is refused if more arrives. Stage 2 removes the file only after a request without a `Range` header, so a download manager that resumes still finds it.
* **Decompression.** The zip disk-space check runs for every extraction (`includes/filesystem-functions/trait-unzip.php`). It was cron-only because the code was copied from WordPress core's `_unzip_file_ziparchive()`; a restore extracts the same archives from AJAX, WP-CLI and cron resumptions, so whether it applied depended only on how the step was dispatched. No test forces a full disk.
* **Shell values from configuration.** `DB_NAME`, the mysqldump and zip program paths, the option file name and `BACKUPPLUS_DIR` are passed through `escapeshellarg()` (`includes/core/trait-binaries.php`, `includes/backup/trait-database-tables.php`, `includes/core/trait-environment.php`). `BACKUPPLUS_BINZIP_OPTS` is split at spaces and each option escaped, but only if every option matches a plain pattern; otherwise it is ignored and logged. `BACKUPPLUS_MYSQLDUMP_MAX_ALLOWED_PACKET` must be a size (`includes/class-executables.php`). A file name with a line break is not sent to `zip -@`; it is added with PclZip after the zip binary has written the rest (`includes/class-zip.php`). `tests/Unit/Backup/ExecutablesTest.php` covers the option splitting, the packet size, the quoting and the line-break detection; adding a real file named with a newline to a binary-zip archive is not run by a test.
* **Template includes.** The template is included from a separate method after `extract( $extract_these, EXTR_SKIP )` (`includes/admin/trait-templates.php`), so a variable named `template_file` or `extract_these` cannot change what is included. `tests/Unit/Backup/AdminHardeningTest.php` passes both and checks that the intended template runs.
* **Range handling.** `bytes=-N` selects the last N bytes, all of a shorter file, and `bytes=-0` or an empty file is unsatisfiable; a last position past the end means the rest of the file; the range is worked out before any header, so an unsatisfiable one gets only a 416 with `Content-Range: bytes */<size>` (`includes/class-partialfileservlet.php`). `tests/Unit/Backup/PartialFileServletTest.php` covers satisfiable and unsatisfiable ranges and checks that no data is sent for the latter. The download helper `spool_file()` answers a multi-range or malformed `Range` header with the whole file and status 200, which RFC 9110 permits, instead of an error.
* **Binary discovery.** `BackupPlus_Executables` (`includes/class-executables.php`) takes programs only from absolute folders that are not world-writable. Folders found on `PATH` or among the standard locations must also not be writable by the PHP user (for root, must be owned by root). Empty, `.` and other relative `PATH` entries are skipped. Links are resolved before the checks. A folder or program the site owner configures (`BACKUPPLUS_PITR_BIN_DIRECTORY`, `BACKUPPLUS_MYSQLDUMP_EXECUTABLE`, `BACKUPPLUS_ZIP_EXECUTABLE`) may be writable by the PHP user, as on shared hosting. Only a value the owner set counts: when the plugin defines the mysqldump or zip constant itself, it marks it as built in (`BACKUPPLUS_*_EXECUTABLE_BUILT_IN`, `BackupPlus_Executables::configured()`), and the default list gets the full checks. The settings page's report follows the same rule. `perl` (the shell check) and `stty` (the WP-CLI secret prompt) go through the same checks. PITR client discovery, the settings page's client report, and mysqldump and zip discovery all use it. `tests/Unit/Backup/ExecutablesTest.php` covers relative, empty, world-writable and PHP-writable entries, configured folders, links and malformed paths.
* **`.htaccess` syntax.** Every private folder gets one file (`BackupPlus_Web_Guard::HTACCESS`, `includes/class-web-guard.php`) with `Require all denied` for Apache 2.4 and `Order deny,allow` / `Deny from all` for Apache 2.2, each inside its own `<IfModule>`. Files that an earlier version wrote are replaced, atomically and with their permissions, by the backup directory, PITR and PITR client writers; a site's own rules are left alone. `tests/Unit/Backup/WebGuardTest.php` covers the branches, that every writer uses the shared contents, and the upgrade.
* **Minor defects that fail closed.** The `doaction` branch is removed (above). Dismissing the restore notice needs a manager and the nonce that the notice's form now actually contains (it was echoed outside the form), sent by POST (`includes/admin/trait-restore.php`). Foreign `.tar`, `.tar.gz` and `.tar.bz2` archives are read with `BackupPlus_Tar`, the plugin's own reader, which accepts only files and directories with safe relative names, after compressed ones are decompressed to a private file within the free disk space (`includes/restorer/trait-unpack.php`); the missing PEAR library is no longer needed. The reader understands POSIX (PAX) long names but not GNU long-name entries or links, so an archive made with GNU tar's defaults that has paths over 100 bytes, or any link, is refused rather than extracted in part. A compressed archive is decompressed again when a restore resumes. `get_outgoing_ip_address()` and `methods/pcloud/BackupPlus_Pcloud_API.php` are removed. The `BackupPlus_<id>auth` nonce mismatch was fixed with BPS-01.

## Reviewed and found sound

These areas were reviewed and no issue was found. They are listed so that future reviews know what was covered.

**Authentication and authorization.** The `backupplus_ajax` dispatcher enforces its nonce before anything runs and re-checks `user_can_manage()` (only three dismiss subactions use `update_plugins`); `call_user_func` reaches only public command methods. `user_can_manage()` uses `manage_options`, or `manage_network_options` on the main site of a network, and sub-site administrators cannot reach any BackupPlus administration surface. Downloads, uploads, settings save and import, the database decrypt download, credential key management and recovery download, source tables, settings wipe, old directory deletion and restore start all check both a capability and a nonce. Pre-update backups use a nonce, a per-batch capability check and a 128-bit batch ID. Heartbeat nonce refresh, log download, `backupplus_spool_file` and `get_log` check the capability and validate the job ID. Every place the credential-test, download and settings nonces are created is gated by `user_can_manage()`. No open redirects were found.

**Cryptography.** The PHP age implementation verifies the header MAC (HKDF of the file key with label `header`) with `hash_equals()`, parses headers strictly (canonical base64, 64-column lines, line, header and stanza limits), rejects an all-zero X25519 shared secret, implements the ssh-ed25519 tweak and RSA-OAEP-SHA256 (minimum 2048 bits) correctly, and implements STREAM with an 11-byte counter and final flag, rejecting truncation, trailing data, empty non-first final chunks and counter exhaustion. Output is staged to a 0600 temporary file and published only after full authentication. The ChaCha20-Poly1305 wrapper requires the full 16-byte tag and verifies it with `hash_equals()`. Credential envelopes use random 96-bit nonces and 256-bit keys, bind version, key ID, blog, option and field path (or job ID and field) as AAD, fail closed, and unserialize with only `stdClass` allowed. The key store uses a 128-bit random directory, 0700 and 0600 permissions, a PHP 404 guard, atomic writes and correct locking; environment-supplied keys never fall back to disk. Settings export omits all provider options. Age restore tickets are `random_bytes( 32 )`, bound to user, blog, time and job. The browser decryptor requires a secure context, bounds the header and scrypt work factor, and publishes plaintext only after authentication. CLI secrets are read from `/dev/tty` with echo disabled and never placed on `argv`. Security-relevant randomness uses `random_bytes()` or phpseclib's CSPRNG, except the job ID (BPS-11).

**SQL.** `BackupPlus_SQL` binds `?` values server-side with `mysqli_prepare()` and `bind_param()`, so binding is unaffected by charset or `NO_BACKSLASH_ESCAPES`. `%a` is a strict allowlist, `%d` is regex-checked, and `%f`, `%l` and `%w` accept only fragments compiled from templates. Every `unserialize()` uses `allowed_classes => false` (or `stdClass` for credentials); the job data store also checks a hash and re-serialization, and search-replace leaves objects as `__PHP_Incomplete_Class`. Restore table prefixes come from WordPress, the temporary prefix is random and checked unused, and dump-derived names reach only `%i`, `?` or the dump's own text. The ordinary restorer strips DEFINER and forces `SQL SECURITY INVOKER`, and skips `GTID_PURGED`, `SQL_MODE`, `USE` and `CREATE/DROP DATABASE`.

**PITR processes and replay.** Credentials reach native clients through a file descriptor 3 pipe, never `argv`, the environment or a file; option names and values reject CR, LF and NUL; files and directories are 0600 and 0700; `--defaults-file` allows only `[client]` connection keys and `--no-login-paths` is set; `PATH` is fixed and `proc_open()` uses no shell; `--binary-mode` disables client commands; remote connections require a CA and verify the server certificate. Binlog replay verifies CRCs, fails closed on unknown events, limits DDL, rejects executable comments and blanks account-control events. Isolation checks use bound values. The grants required by the code match `docs/binary-log-backups.md`.

**Archives and files.** The tar reader rejects absolute paths, `..`, backslashes, NUL and drive letters, accepts only files and directories, and verifies checksums. ZIP extraction validates every entry and writes symlink entries as regular files. PITR archive members are tied to the manifest and SHA-256 verified. Chain downloads, backup deletion, retention, the database decrypt download, `backupplus_spool_file`, log download, `fetch_log`, age plaintext upload, `plupload_action2`, the restore inventory, incremental v2 deletion paths and multisite uploads restore all validate names. Every dynamic include uses a constant or internally validated path. Temporary files use random names in private directories. mysqldump `--where`, user, host and table name are escaped. SFTP remote commands use `escapeshellarg()`.

**Remote storage.** TLS verification is on by default for every provider, using the bundled CA bundle; `disableverify` is off by default and clearly labelled. `BackupPlus_Remote_Storage_HTTP` (Azure, Backblaze, Google Cloud, OneDrive, pCloud) allows only HTTPS on port 443 to an allowlisted host checked on every URL including server-returned ones, follows no redirects, restricts cURL to HTTPS and bounds response sizes. OneDrive and pCloud OAuth state handling is correct. SFTP and SCP require a pinned SHA-256 host key fingerprint before sending credentials; there is no trust on first use. FTP over TLS uses `CURLUSESSL_ALL` with peer and host verification. WebDAV follows no redirects and keeps credentials out of URLs. ntfy follows no redirects. The GitHub recipient fetch uses HTTPS with verification, no redirects and a size cap. No log line was found that writes a password, secret or token, and restore options redact the passphrase.

**Output escaping.** The backup table template uses `esc_attr()` and `esc_html()` throughout; Handlebars triple braces are used only for developer-controlled strings; imported settings render through escaped double braces; `fetch_log`, the last log message, `httpget` output (the tool has since been removed, BPS-20) and settings-page `error`/`message` parameters are escaped; restore activity output goes through `wp_kses_post()`. There are no window `message` listeners and no `eval()` or `new Function()` in the admin sources.
